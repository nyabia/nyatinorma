# nyatinorma

pi의 모델 provider와 TUI로 실행하는 로컬 computer-use 에이전트입니다. 독립 실행에는 Bun, Tauri, 별도 모델 서버가 필요하지 않습니다. 같은 저장소의 `integrations/omp`는 공통 sleepwalk 실행기를 omp의 기존 computer 인터페이스에 연결합니다.

기본 프리셋은 없습니다. 자연어로 작업을 요청하면 모델이 관측하며 진행하고, 재사용할 절차를 발견하면 스스로 프리셋·지식·후보 세트로 저장합니다. 저장은 새 작업 실행을 뜻하지 않습니다.

현재는 실험적인 소스 배포입니다. Node.js 22.19 이상, npm, 별도로 설치한 `cua-driver`, 이미지 입력을 지원하는 모델 서버가 필요합니다. 설치 프로그램과 자동 업데이트 명령은 아직 제공하지 않습니다.

## 실행

```sh
git clone https://github.com/nyabia/nyatinorma.git
cd nyatinorma
npm ci
cp nyatinorma.example.json nyatinorma.json
# nyatinorma.json에서 실제 모델명과 대상 앱을 설정
npm run doctor
npm start
```

이미 설치했다면 `npm start`만 실행합니다. macOS는 `nyatinorma.command`, Windows는 `nyatinorma.cmd`도 사용할 수 있습니다. 선택 메뉴 없이 바로 입력할 수 있고, 이름 없는 임시 기록이 자동 생성·저장됩니다. `/save 이름`은 현재 기록에 이름을 붙이며 `/runs`에서 임시 기록도 다시 열 수 있습니다. `npm start -- --continue`는 이전 대화를 이어갑니다.

TUI에서 `/play` 또는 자연어로 작업을 지시합니다. `npm start` 자체는 게임 입력을 시작하지 않습니다.

상시 안내는 `자연어로 요청하세요 · /help 도움말` 한 줄입니다. 명령과 이력 탐색 설명은 `/help`에서 확인합니다.

앱 자체 자동진행 기능이 요청에 적합하면 이를 이용할 수 있습니다. `ny_wait(seconds)`는 지정한 시간 뒤 한 번 관측하고, `ny_wait(until)`은 화면 조건을 입력 없이 반복 확인합니다. `/stop`과 Escape는 에이전트를 멈추며, 앱 자체 자동진행까지 해제하지는 않습니다.

| 명령 | 동작 |
|---|---|
| `/preset` 또는 `/task` | 프리셋으로 독립된 새 실행 생성 |
| `/save 이름` | 현재 기록에 이름 붙이기; 저장은 이미 자동으로 진행됨 |
| `/runs` | 임시 기록을 포함한 이전 실행 선택·연결 |
| `/chat` | 이전 기록을 보존하고 새 임시 기록으로 대화 |
| `/newtask 목표` | 재사용할 프리셋 생성, 실행은 만들지 않음 |
| `/play [이번 범위]` | 현재 기록에서 지정한 범위 진행 |
| `/new` | 새 대화와 빈 임시 기록 |
| `/tree` / `/fork` | 이전 대화 지점으로 이동 / 별도 대화로 분기 |
| `/resume` | 저장된 대화 재개 |
| `/help` | 기본 사용법과 이력 기능 안내 |
| `/plan` | 단계별 실행 계획과 미확인 항목 확인 |
| `/feedback 교정 내용` | 사람의 피드백을 관측 ID와 저장하고 개선 요청 |
| `/sets` | 현재 작업의 후보 세트 목록 |
| `/trace` | 최근 선택·실행·검증 기록 |
| `/doctor` | Cua 권한·대상 창 확인 |
| `/stop` 또는 Escape | 현재 실행 취소 |

## 모델과 커스텀 서버

모델 선택은 pi 기본 `/model`을 사용합니다. 별도의 “커스텀 추가” 항목 대신, `.nyatinorma/pi/models.json`의 `providers`에 서버를 등록하면 `/model`을 열 때 목록을 다시 읽습니다. pi 설정을 프로젝트 안에 격리하므로 전역 `~/.pi/agent/models.json`을 수정하는 경로와 다릅니다.

스킬 자동 탐색과 `/skill:<name>` 명령은 기본 활성입니다. pi의 프로젝트/에이전트 스킬 경로를 사용하며, 외부 스킬은 `--skill <SKILL.md 경로>`로 명시합니다. 기본 도구에 읽기 전용 `read`를 포함해 스킬 목록과 본문·참조 파일을 사용할 수 있습니다. nyatinorma의 시스템 프롬프트는 역할 설명만 교체하므로 pi의 스킬 섹션을 보존합니다. 셸 실행·파일 수정 도구는 기본 활성화하지 않습니다. 기존 설정에 `enableSkillCommands:false`가 저장돼 있다면 `true`로 바꿔야 합니다.

SGLang 등 OpenAI 호환 서버 예시(기존 providers 항목은 보존하세요):

```json
{
  "providers": {
    "my-server": {
      "baseUrl": "http://localhost:8000/v1",
      "api": "openai-completions",
      "apiKey": "local",
      "models": [{
        "id": "your-vision-model",
        "reasoning": false,
        "input": ["text", "image"],
        "contextWindow": 32768,
        "maxTokens": 4096
      }]
    }
  }
}
```

실제 모델 ID는 서버의 `/v1/models`로 확인합니다. 이미지·추론 지원과 한도는 모델에 맞게 설정합니다. 인증 서버는 pi가 지원하는 환경변수 참조(예: `$MODEL_API_KEY`)를 사용하세요. `apiKey: "local"`은 인증 없는 로컬 서버에만 쓰는 자리표시자입니다. 호환성 옵션은 해당 서버에서 확인한 값을 넣습니다.

시작 시 provider/model을 강제하지 않으며 pi의 저장된 선택과 명시적 `--provider`/`--model` 옵션을 따릅니다. 기본 Ollama는 `nyatinorma.json` 설정으로 추가 등록하는 선택지입니다. 서버를 추가한다고 기존 Ollama가 내려가거나 설정이 바뀌지 않습니다.

THINK와 후보 생성은 pi의 현재 provider 연결을 사용합니다. 기본 SELECT도 현재 선택된 모델을 사용하며, OpenAI 호환 경로는 pi의 인증·주소·추론 호환 설정을 재사용합니다. 네이티브 Ollama와 OpenAI Chat Completions logprobs 경로를 지원하고, logprobs 누락/불완전한 점수는 실행 없이 THINK로 반환합니다. 그 밖의 API는 THINK/직접 행동을 사용할 수 있지만 legacy SELECT는 지원 오류를 알립니다.

vLLM의 Qwen 추론 모델에서 effort를 지원한다면 모델의 `compat`에 `thinkingFormat:"qwen-chat-template"`와 `supportsReasoningEffort:true`를 지정합니다. nyatinorma는 pi가 만든 `chat_template_kwargs.enable_thinking:true`를 유지하면서 현재 추론 단계(예: `/thinking low`)를 `reasoning_effort:"low"`로 보완합니다. 모델의 `thinkingLevelMap`과 이미 지정된 effort를 존중하며, 추론이 꺼진 SELECT·후보 생성에는 effort를 추가하지 않습니다. 새 세션 기본값은 `.nyatinorma/pi/settings.json`의 `defaultThinkingLevel:"low"`이고, 재개한 세션은 기존 단계가 남을 수 있으므로 `/thinking low`로 명시합니다. 확장 코드 변경은 `/reload` 또는 재시작 후 적용됩니다.

### 선택적 System One 판정

`nyatinorma.json`에 `decision`을 지정하면 THINK/후보 생성 모델은 그대로 두고 빠른 SELECT만 decision-native 모델에 맡깁니다. 기존 경로로 돌아가려면 `decision`을 지우거나 `mode:"legacy"`를 사용합니다.

```json
{
  "decision": {
    "mode": "systemone",
    "url": "http://127.0.0.1:11434",
    "model": "d3:4b",
    "wire": "ollama",
    "timeoutMs": 30000,
    "fallback": true
  }
}
```

`wire:"ollama"`는 `/v1/systemone`의 top-level `images` 배열을 사용합니다. Jev/TypeSafe 서버는 `wire:"typesafe"`로 asset 참조 형식을 사용합니다. 인증이 필요한 서버는 `headersFromEnv:{"Authorization":"SYSTEMONE_AUTHORIZATION"}`처럼 헤더 값을 환경변수로 참조합니다. 해당 환경변수에는 `Bearer …` 등 서버가 요구하는 전체 헤더 값을 넣고 설정 파일에는 비밀값을 저장하지 않습니다.

기본 `fallback:true`는 System One의 통신·응답 오류를 기존 SELECT 경로로 전환하며 전환 사실을 표시합니다. `fallback:false`는 오류를 그대로 반환합니다. 사용자 취소는 폴백하지 않으며, 낮은 선택 점수 자체를 서버 고장으로 취급하지 않습니다. 모델 전환은 판정 요청에만 적용되고 입력을 재전송하지 않습니다.

System One 설정은 Ollama 모델 다운로드, GPU 배치, 실제 `num_ctx`, THINK의 컨텍스트 한도를 바꾸지 않습니다. [Ollama System One 문서](https://docs.ollama.com/api/systemone)의 이미지·요청 크기 한도를 따릅니다.

### omp 통합

`integrations/omp`는 별도 저장소가 아니라 이 저장소의 플러그인 패키지입니다. 루트에서 `npm ci`, `npm run build:omp`, `omp plugin link ./integrations/omp`를 실행하고 omp를 재시작한 뒤 `nyatinorma_setup`을 호출합니다.

| 역할 | 담당 |
|---|---|
| 목표·행동 후보·완료 조건, 막힌 상황의 새 판단 | 상위 모델 |
| 행동 선택·클릭 대상 검증 | omp `judge()` 또는 선택한 System One 모델 |
| 대기·스크롤·행동·결과 확인·중단·재개 | nyatinorma 공통 `runExecution` / `runAct` |
| 실제 창 캡처·클릭·드래그 | omp의 기존 `computer` |

`wait / scroll / act / status / stop / resume`를 제공합니다. 판정 모델만 로컬로 바꿔도 상위 계획까지 자동으로 대체되지는 않습니다. 설치·후보 형식·취소·입력 보호는 [omp 사용 가이드](integrations/omp/USAGE.md)를 참고하세요.

## 입력 드라이버와 다른 프로그램 격리

**독립 pi/CLI 실행의** 기본 드라이버는 `cua-driver mcp`입니다. 아래 Cua·macOS 브리지 설정은 이 경로에 해당하며, omp 통합은 omp `computer`를 사용합니다. 독립 실행은 자체 MCP 클라이언트와 고유 세션만 정리하고 공용 데몬의 종료·재시작·업데이트·전역 설정 변경은 하지 않습니다.

macOS 캡처와 클릭은 cua-driver **0.9.0**에서 시험했습니다. 새 환경에서는 Cua 설치와 해당 앱의 macOS 권한 설정이 필요합니다. 일부 macOS iPad 앱은 백그라운드 클릭에 `cuaModifiers:["cmd"]`가 필요할 수 있습니다. 이 옵션은 호출 인자로만 전달하고 드라이버 전역 설정을 바꾸지 않으며 Windows에서는 보내지 않습니다.

**드래그는 별도 어댑터로 분리했습니다.** 시험한 macOS Cua 버전은 백그라운드 드래그를 거부합니다. 지원 범위는 [Cua 지원표](https://github.com/trycua/cua/blob/main/libs/cua-driver/docs/action-support.md)를 확인하세요. `dragDriver:"macos-bridge"`를 명시하면 드래그만 `Nyatinorma Bridge.app`에 보냅니다. `ny_drag`, SELECT의 드래그 모두 같은 어댑터를 사용합니다. Cua가 캡처한 창의 PID·ID·위치·크기를 브리지와 대조한 뒤 background 입력을 보내며, 결과는 Cua 이미지로 검증합니다. macOS 시험에서 목록 드래그, 커서 위치와 활성 앱 유지를 확인했습니다.

macOS 브리지가 필요하면 Xcode Command Line Tools의 Swift 컴파일러로 `npm run build:native`를 실행합니다. 생성된 `Nyatinorma Bridge.app`에 시스템 설정의 손쉬운 사용·화면 기록 권한을 허용해야 합니다. 빌드된 앱은 소스 저장소에 포함하지 않습니다. 공용 Cua 설치본을 수정하지 않습니다.

`nyatinorma.json`의 주요 설정:

- `driver:"cua"`: 기본 캡처·클릭 드라이버입니다. 자체 브리지 전체 기능은 `"macos-legacy"`를 명시한 경우에만 사용하며 자동 fallback은 없습니다. 드래그는 아래 별도 설정으로 선택합니다.
- `dragDriver:"macos-bridge"`: macOS에서 드래그만 별도 브리지로 보냅니다. 기본값 `"cua"`는 Cua만 사용하며 macOS의 미지원 드래그를 거부합니다. Windows에서는 항상 Cua 드래그를 사용하고 macOS 브리지를 실행하지 않습니다.
- `cuaDriverPath`: 기존 실행 파일 또는 프로젝트 전용 실행 파일의 경로. 기본 `cua-driver`.
- `targetApp`: TUI에서 최초 대상 선택의 힌트, CLI에서는 기본 대상 앱 이름 또는 정확한 창 제목입니다. 기본값은 비어 있으며 TUI의 세션 선택을 고정하지 않습니다.
- `targetPid`, `targetWindowId`: CLI의 고정 대상 지정입니다. TUI에서는 모델이 `ny_target`으로 선택한 창이 우선합니다. PID/창 ID는 앱 재시작 후 바뀔 수 있습니다.
- `cuaModifiers`: macOS용 입력 보조키. 기본값은 `[]`이며 대상 앱에 필요한 경우에만 지정합니다.

TUI에서는 자연어로 대상 앱을 지정하면 모델이 `ny_target({operation:"list"})`로 실행 중인 창의 앱 이름·제목·PID·창 ID를 읽고, `select`로 선택합니다. 목록 조회와 선택 자체는 캡처·클릭·포커스 변경을 하지 않습니다. 선택은 대화에 저장되고 재개·분기에 복원됩니다. 새 대화에서는 다시 선택합니다. 이후 캡처 시 같은 앱의 창 ID가 바뀌었으면 후보가 하나일 때만 재연결하고, 없거나 여러 개면 모델이 목록을 보고 다시 선택합니다. 과거 창의 좌표는 새 창에 그대로 보내지 않습니다.

다른 앱이나 다른 창을 명시적으로 선택하면 기존 진행을 보존하고 별도 임시 기록을 만듭니다. 기존 중단·입력 미확정 상태와 마감을 우회하지 않습니다. 앱 지식·프리셋·후보 세트도 선택한 앱 기준으로 분리하며 전역 설정 파일은 수정하지 않습니다. 다른 앱의 이전 실행을 불러오려면 그 앱을 먼저 선택하세요.

macOS의 임의 앱 PID를 지정하는 브리지 경로와 `macos-legacy`의 창 목록은 Bridge protocol 5 소스에 추가되었습니다. 기존 바이너리 사용자는 현재 작업을 종료한 뒤 `npm run build:native`, `npm run bridge:restart`로 갱신해야 합니다. 브리지는 자동으로 교체·재시작하지 않습니다. 이번 창 선택 변경은 아직 실행 검증하지 않았습니다.

캡처는 지정 창 하나만, 입력은 `delivery_mode:"background"`만 사용합니다. foreground로 자동 전환하지 않습니다. 게임 창을 최소화하거나 닫지 마세요. 드라이버가 입력을 전달했다는 응답만으로 클릭 성공을 판단하지 않고, 실행 후 이미지를 다시 확인합니다. Cua가 반환하는 AX/UIA 텍스트는 모델에 전달하지 않습니다.

Nyatinorma가 생성·복구하는 Cua 전용 세션은 커서 이동을 고정 **1ms**, 클릭 후 시각적 대기를 **0ms**로 설정합니다. Cua의 `glide_duration_ms:0`은 즉시 이동이 아니라 거리 기반 애니메이션이므로 사용하지 않습니다([Cua 0.22.1 구현](https://github.com/trycua/cua/blob/cua-driver-rs-v0.22.1/libs/cua-driver/rust/crates/platform-windows/src/tools/impl_.rs#L263)). 실제 드래그의 `duration_ms`, 공유 데몬 설정, 다른 세션의 커서는 바꾸지 않습니다. 이는 커서 애니메이션 대기 제거이며 모델 판단·캡처·실제 입력 전체가 1ms에 끝난다는 뜻은 아닙니다.

**Windows 독립 실행:** Windows용 cua-driver와 접근 가능한 모델 서버가 필요합니다. Node 24.13에서 `doctor`, MuMu 창 캡처, clef-flash System One SELECT, Spark OpenAI 호환 계획 모델의 이미지 응답을 확인했습니다. Cua 경로의 게임 입력은 미검증이며 omp 실기 결과와 구분합니다. 모델 연결 성공이 화면 해석의 정확성을 뜻하지는 않습니다. `nyatinorma.cmd`로 시작합니다. `tsx` 실행 파일이 없으면 저장소 루트에서 `npm install`로 의존성을 복구하세요. Spark처럼 OpenAI 호환 API만 제공하는 서버는 pi `models.json`의 `baseUrl`로 등록하고 `settings.json`의 기본 모델을 선택합니다. 이를 Ollama 전용 `ollamaUrl`에 넣지 마세요. 원격 서버의 네트워크 설정은 변경하지 않습니다. [Cua Windows API](https://cua.ai/docs/reference/cua-driver/mcp-tools-windows)

별도 버전이 필요하면 `cuaDriverPath`로 실행 파일을 지정하는 구조입니다. 프로젝트는 Cua를 자동 설치·업데이트하지 않습니다. 자체 브리지 전체 기능은 `driver:"macos-legacy"`를 명시한 경우에만 사용합니다. 드래그만 필요하면 `dragDriver`를 설정하세요.

macOS에서는 MCP 세션은 별개지만 Cua 데몬은 기존 설치본을 공유합니다. 따라서 별도 실행 파일 경로 지정만으로 데몬까지 격리되는 것은 아닙니다. 향후 드라이버 수정이 필요하면 독립 서비스 주소·앱 식별자·권한 소유자까지 분리해서 검증해야 합니다.

좌표 탐색의 MOVE는 확대 영역 경계를 넘어갈 수 있으며, 가장자리에 가까워지면 확대 배율을 유지한 채 관측 영역이 따라갑니다. 이동 후보 그림에는 확대 영역 밖의 이웃 픽셀도 포함합니다. 실제 앱 창 밖의 좌표는 허용하지 않으며, 구석의 대상도 화면 중앙으로 옮길 필요 없이 내부 클릭점으로 확인합니다.

SELECT 기반 위치 탐색에서는 클릭 위치를 넓은 화면의 YES만으로 확정하지 않습니다. 아직 넓은 영역을 보고 있다면 같은 십자선 좌표 주위의 최대 160×160 원본 픽셀 영역을 확대하고 전체 창과 함께 다시 SELECT로 확인합니다. 이미 그보다 좁은 영역에서 확인했다면 중복 확인을 생략합니다. NO/불확실은 기존 MOVE·확대 탐색으로 이어지며, 전체 20회 SELECT 예산을 넘기면 클릭하지 않습니다. 이 변경의 실제 게임 정밀도는 아직 검증하지 않았습니다. `ny_click` 직접 클릭에는 이 SELECT 탐색·확인을 적용하지 않습니다.

### 진행 중 판단 이미지

`ny_act`, `ny_scroll`, `ny_locate`, `ny_drag`, SELECT 세트, 저장 flow와 조건 대기에서 모델에 보내는 최신 판단 이미지를 진행 중 도구 결과에 표시합니다. 격자·클릭 십자선·드래그 화살표·이전/현재 비교도 실제 입력 이미지 그대로 표시합니다. 새 프레임이 이전 프레임을 교체하며 중간 이미지를 상위 모델의 대화에 추가하지 않습니다. 최종 결과 이미지는 기존처럼 대화에 남습니다.

기본 ON이며 `/preview off`로 끄고 `/preview on`으로 켭니다. pi의 `terminal.showImages` 설정을 따릅니다. Kitty/iTerm2 지원 터미널에서는 pi가 원본 이미지를 표시하고, 일반 터미널에서는 MIT 라이선스의 [`terminal-image`](https://github.com/sindresorhus/terminal-image)가 색상 블록으로 변환합니다. macOS Terminal.app·Windows·Linux에서 공통으로 사용하는 방식이며 bash/zsh 선택과는 관계없습니다. 블록 표현에서는 작은 글씨와 정밀한 위치가 흐릿할 수 있습니다. 변환 결과는 화면 표시용 메모리에만 두며, 별도 PNG 저장이나 모델 호출은 하지 않습니다. nyatinorma에는 pi 연결 코드만 있으며 픽셀 변환·이미지 프로토콜 구현은 없습니다. 실제 터미널별 표시는 아직 실행 검증하지 않았습니다.

## THINK / SELECT

- **THINK:** pi 일반 대화·이미지 도구 루프. 모델은 `ny_reasoning`으로 다음 계획 요청의 추론을 켜거나 끌 수 있고, 후보 정의 오류가 연속 두 번 나면 하네스도 추론을 켭니다. 이 설정은 현재 pi 세션에만 적용됩니다. 선택된 pi provider의 스트리밍으로 목표, 관측, 후보와 복구 계획을 만듭니다. Ollama 네이티브 연결도 선택할 수 있습니다.
- **SELECT:** 확장의 짧은 루프. 기본 경로는 현재 provider의 추론을 끈 1토큰 `logprobs`를 사용하며, 선택적 System One 경로는 typed-choice 판정 분포를 사용합니다. 두 경로 모두 같은 sleepwalk 실행기로 연결됩니다.
- **ACT:** `ny_act({goal, until?, constraints?, grid_navigation?})`는 작은 목표를 수행합니다. 기본 모드는 현재 실행에 등록한 좌표 클릭만 사용하며 생성 드래그·암묵적 격자 탐색도 꺼져 있습니다. `ny_act_point_add`로 대상을 등록하거나 `ny_locate`로 찾은 좌표를 등록합니다. `grid_navigation:true`를 명시하면 기존 생성 클릭·드래그·격자 탐색도 허용합니다. `ny_scroll`은 독립적인 드래그 전용 실행입니다. `ny_act({resume:continuationId})`로 재개하며 입력 뒤 결과를 확인합니다. 후보 생성은 planner 추론 설정을 변경하지 않습니다.
- **드래그 sleepwalk:** `ny_scroll({goal:"현재 목록에서 요청한 항목을 찾는다",until:"해당 항목의 제목이 분명하게 보인다"})`도 ACT와 같은 실행기를 사용합니다. 드래그만 허용하며, SELECT로 이동·발견·거리 조정·종료를 판단합니다. 이동량은 큰 탐색과 작은 조정 두 단계입니다. 기본 호출당 80회, 최대 300회이며 시간 예산과 사용자 마감은 유지합니다. 큰 이동은 창 축 길이의 55%, 작은 이동은 8%부터 경로를 확인하고, 영역을 벗어나거나 경로 확인이 실패하면 더 짧은 후보를 확인합니다. 이는 손가락 이동 거리이며 실제 콘텐츠 이동량은 앱에 따라 다릅니다. 큰 탐색 드래그 후에는 0.2초 뒤 확인하고, 관성이 남아도 판독 가능하면 이어갑니다. 이동 때문에 판독·미세 조정이 어려울 때만 기다리며, 작은 조정 후에는 0.7초 대기를 유지합니다. 목표 발견 시 직전·최신 화면을 비교하여 잠깐 지나가는 항목을 완료로 오인하지 않도록 확인합니다. 모델 추론과 캡처 시간은 별도입니다. 매 스크롤마다 상위 모델로 돌아가지 않습니다. 호출 예산에 도달하면 `resume`으로 이어가며 드래그 전용 제한도 보존합니다. 기본 도구 `ny_scroll`은 목표·종료 조건을 받으며 좌표를 받지 않습니다. `ny_drag`는 `ny_tools`의 legacy 그룹에서 제공하는 별도 단발 도구로, 기존 `snapshotId`·좌표 인자를 받습니다. 클릭·화면 이동까지 필요한 목표는 `ny_act`를 사용합니다. 이번 연결은 실행 검증하지 않았습니다.
- 후보 세트의 `purpose`는 이번 화면에서 할 일입니다. 예를 들어 전체 목표는 별 3개 클리어여도 지금 목표는 "전투 목록을 열어 별 수 확인"입니다. SELECT에는 두 목표를 함께 전달합니다.
- **OCR을 사용하지 않습니다.** 모델이 게임 창 이미지와 crop을 직접 읽고 시각적 대상을 지정합니다. Cua의 AX/UIA 결과는 버리고 이미지와 창 메타데이터만 사용합니다.
- 후보 세트의 `visualAnchors`는 제목·선택된 탭·팝업 테두리 등 정적인 이미지 영역 1~4개입니다. 실제 관측에서 화면 앵커와 대상 템플릿을 추출하고, 모델 응답을 받은 후 새 화면에서 다시 비교합니다. 단색 앵커는 거부합니다.
- 대상 비교는 ±2픽셀의 렌더링 오차만 허용합니다. 더 크게 움직이거나 이미지가 달라지면 THINK로 돌아가 확대 관측 후 후보를 새로 만듭니다. 이미지 비교는 의미 이해를 보장하지 않습니다. SELECT 기반 실행은 모델에도 화면을 전달하며, 직접 `ny_click`의 대상 정체성과 결과는 planner가 판단합니다.
- 기존 OCR 기반 세트는 자동 실행하지 않고 새 이미지 기반 세트로 다시 작성하도록 안내합니다. 과거 버전은 기록으로 보존합니다.
- 정밀 클릭에는 4×4 격자를 사용할 수 있습니다. `ny_observe`에서 `grid:true`로 A1~D4 칸을 보고, `regionPath:["C4"]`로 확대합니다. 다시 D3 칸을 선택하면 `regionPath:["C4","D3"]`를 후보에 넣습니다. 코드가 전체 창 좌표를 계산하므로 모델이 x+width 같은 산술을 할 필요가 없습니다. 격자는 모델에게 보여주는 이미지에만 그리며, 원본·템플릿은 변경하지 않습니다. `visualAnchorRegions`도 같은 경로를 받습니다.
- 셀 중앙 외의 위치는 `gridPoint:{regionPath:["C4"],x:0.2,y:0.8}`처럼 지정합니다. 이는 **C4 내부에서 왼쪽으로부터 20%, 위에서부터 80%**이며, 전체 창 좌표 변환은 코드가 처리합니다. `ny_click`, `ny_drag`, SELECT 후보와 flow 행동에서 동일하게 사용하며 드래그 도착점에는 `toGridPoint`를 씁니다. 기존 `point`는 전체 창 기준, `regionPath` 단독은 셀 중앙입니다.
- `ny_preview`에 `snapshotId`와 같은 좌표 인자를 주면 **클릭 없이** 십자선·좌표를 표시한 전체 이미지와 확대 이미지를 돌려줍니다. 위치가 맞으면 같은 인자를 행동 도구에 넘깁니다. 선택적인 확인 도구이며, 원본 캡처나 관측 시각을 변경하지 않고 실제 행동의 화면 검증도 생략하지 않습니다.
- `ny_time`은 현재 현지 시각·시간대·UTC를 조회합니다. `nextLocalTime:"03:00"`을 주면 컴퓨터 시간대에서 다음 해당 시각의 날짜까지 계산합니다. `operation:"set_deadline"`과 함께 주면 현재 실행의 일회성 마감으로 저장합니다. 날짜가 정해진 제한은 `stopAt`에 시간대 오프셋을 포함한 ISO 시각을 지정하며, 지난 시각도 그대로 만료 처리합니다. 마감은 재시작·재개 후에도 유지되고 자동 연장되지 않습니다. 반복 실행과 입력 직전에 검사하여 늦게 도착한 모델 응답이 새 클릭을 보내지 못하게 합니다. 이미 보낸 입력과 **게임 자체 자동진행**은 중단하지 않으므로, 자동진행까지 끄려면 마감 전에 해당 UI 작업을 수행하도록 요청해야 합니다. 사용자 지시에 따른 해제는 `operation:"clear_deadline"`입니다.
- `intent`는 자유로운 행동 설명이며 작업 전용 enum이 없습니다. 추가 관측 정보는 후보의 `data` 객체에 담습니다.
- 확대는 원본 스크린샷 crop입니다. 확대 결과에는 전체 창 이미지도 함께 제공해 화면 밖 번호나 상태를 추정하지 않도록 돕습니다. 모든 저장 좌표는 **전체 창 기준 0–1**이며 Cua 캡처 픽셀로 변환한 뒤 드라이버가 실제 입력 좌표로 변환합니다.
- Cua 캡처의 원본 크기와 픽셀 좌표를 그대로 보존합니다. Retina/DPI 변환은 드라이버가 담당합니다.
- 매 모델 요청에는 가장 최근 관측 묶음의 이미지를 전달합니다. 한 번에 여러 crop 도구를 호출했다면 그 묶음은 모두 유지해 별 판독의 근거가 누락되지 않게 합니다. 이전 묶음은 ID·텍스트와 로컬 원본으로 남아 다시 확대할 수 있습니다.
- 이미지 입력은 지정된 **게임 창**과 그 창의 crop/격자 이미지입니다. 바탕화면 전체를 보내지 않습니다. 이미지 옆에 관측 ID, 전체/확대 이미지 순서, 영역 좌표를 명시합니다. 작업 지침·도구 정의·대화 기록도 텍스트로 입력됩니다.
- 불완전한 top-k와 낮은 선택 점수는 입력 근거가 아닙니다. 실행기는 드래그 결과와 목표를 현재 화면에서 판정하고, 범위 변경이나 미해결 판단이 필요할 때 THINK로 돌아갑니다.

확률은 **보정되지 않은 모델 선택 점수**입니다. legacy 경로는 토큰 logprobs, System One 경로는 선택 분포를 사용합니다. `selectMinMass`·`selectMinMargin`·템플릿 임계값은 초기 보수적 설정이며 실제 성공률을 뜻하지 않습니다. 불완전한 후보 분포를 입력 근거로 쓰지 않습니다. 입력 prefill과 공유 서버의 대기 시간은 빠른 선택으로 사라지지 않습니다.

공유 서버의 대기를 고려해 legacy `ollamaTimeoutSeconds`는 기본 **600초(10분)**, SELECT 구간의 `maxRunSeconds`는 **900초(15분)**입니다. System One 요청 시간 제한은 별도의 `decision.timeoutMs`입니다. `nyatinorma.json`에서 변경한 뒤 TUI를 다시 열면 반영됩니다. 긴 요청 중에도 Escape로 취소할 수 있으며, 응답을 오래 기다린 경우에도 입력 직전에 화면과 창 좌표를 재검증합니다. 동일 서버로의 무조건적인 재시도는 하지 않으며, System One 실패 시 기존 경로 전환 여부는 위 `fallback` 설정을 따릅니다.

## 작업과 개선

**스킬 패키지**는 앱의 재사용 지식·프리셋·후보 세트·근거 자료를 묶습니다. **실행 기록**은 이번 계획·진행·후보·로그이며 **대화**는 pi 세션입니다. 시작할 때 실행 생성이나 프리셋 선택을 요구하지 않습니다. 모델은 현재 임시 기록에서 바로 작업하고, 필요하면 `ny_run configure`로 프리셋을 적용하거나 이름을 붙입니다. 이때 기록 ID와 진행은 보존됩니다. `/preset`은 별도 실행을 명시적으로 만들 때 사용합니다.

새 대화·`/tree`·`/fork`에는 이전 진행이 섞이지 않은 임시 기록을 자동으로 만듭니다. `/resume`은 그 대화의 기록 연결을 복원합니다. 과거 대화로 돌아가도 게임 상태는 돌아가지 않으므로 입력 전에 새 화면을 관측합니다. 같은 실행을 여러 터미널에서 동시에 변경하는 것은 잠금으로 막습니다. 임시 기록은 작업 지시가 아니며, 질문만 하면 게임을 조작하지 않습니다.

지식은 **공통 조작 → 앱 공통 → 상황별**로 구분합니다. 공통/앱 지식과 상황 목록을 기본 제공하고, 모델은 `ny_knowledge use`로 현재 상황을 선택합니다. 상황별 지식은 다른 작업에 무조건 주입하지 않습니다. `read`로 검색·조회하고 `remember`로 새 지식을 보존합니다. 스크린샷이 있는 메모는 `observed`, 아직 가설이면 `hypothesis`로 저장하며, `supersedes`로 잘못된 메모를 대체해도 원문은 남습니다. `evidence`로 과거 근거 이미지를 다시 볼 수 있습니다. 오래된 근거는 현재 게임 상태를 뜻하지 않습니다.

전체 메모를 매번 전송하지 않고 짧은 최근 요약만 주입하며 필요할 때 검색합니다. 성공 후에는 재사용할 발견을 저장하고 필요하면 프리셋을 만든 뒤 후보 세트를 검증·등록하도록 모델에 지시합니다. 저장은 도구 호출로 이루어지며, 모델의 발견이나 이미지 판독이 자동으로 정확해지는 것은 아닙니다.

기존 태스크별 진행/계획/후보/로그는 원본을 보존한 채 `이전 기록 · …` 실행으로 가져옵니다. 과거 테스트가 새 대화에 강제로 주입되지 않습니다. 이력 기능은 입력창 맨 위의 ↑, PageUp/PageDown, `/tree`, `/fork`, `/resume`을 사용하며 `/help`에도 표시합니다.

작업 정의와 select set 수정본은 이전 버전을 보존합니다. 모델은 `ny_history`로 실패와 사용자 피드백을 읽고 `ny_define_set`으로 수정하고, 과거 관측에 `validate`를 실행하거나 `rollback`으로 되돌릴 수 있습니다. 이는 **작업·탐색 정책의 개선**이지 가중치 학습이나 정확도 향상 보장이 아닙니다. `validate`는 화면/대상 재인식 검사이며 게임 성공률 검증은 아닙니다.

`ny_plan`은 선택적인 작업 메모로, 현재 구간의 단계·진행 중 항목·완료 근거·막힌 이유·미확인 항목을 실행별로 저장합니다. 실행기가 확인된 진행을 기록하므로 계획 작성은 ACT의 선행 조건이 아닙니다. 모델 요청에는 현재 실행 목표·마지막 입력·최근 근거와 계획의 활성 단계·미확인 항목만 참고용으로 제공합니다. 전체 계획은 `ny_plan get`으로 읽을 수 있습니다. `/plan`으로 사람이 확인하고 `/feedback`으로 교정할 수 있습니다. 계획 완료는 스크린샷 참조가 필요하지만, 이미지 의미를 자동 검증하거나 전투 별 기록을 대신하지 않습니다. 장기 작업은 구간별로 계획을 갱신합니다.

`ny_block`은 모델이 구체적인 진행 불가 사유를 판단했을 때 쓰는 종료 도구입니다. 사유·시도한 방법·진행 상황·필요한 개입을 저장하고 현재 에이전트 실행을 종료하므로, 보고서를 쓰기 위한 추가 추론도 발생하지 않습니다. 시도 목록은 비워도 되며 정상 대기나 필요한 반복 횟수만으로 자동 발동하지 않습니다. 중단 상태는 재시작·재개 후에도 유지되고, 후속 입력과 모델의 새 실행 생성 우회도 차단합니다. 사용자 질문에 대한 설명과 기록 조회는 가능합니다. 준비되면 **`/play [교정 내용]`**으로 같은 기록에서 재개하며 새 화면부터 확인합니다. 기존 마감 시각은 그대로 유지합니다. 막힘 판단은 모델에 의존하지만, `ny_block` 호출 후 종료는 코드가 수행합니다. 게임 자체 자동진행을 끄는 기능은 아닙니다.

세트는 실행별로 독립됩니다. `ny_history publish`로 관측 검사를 통과한 세트와 검증 이미지를 스킬 안의 프리셋 라이브러리에 저장하면 새 실행이나 명시적 프리셋 적용 때 재사용합니다. 기존 실행의 세트를 덮어쓰지 않습니다. 임시 기록에서 만든 세트를 공유하려면 재사용 프리셋에 연결합니다. 모델의 작업 상태에는 현재 세트 목록이 표시됩니다. 일반 작업은 `ny_act`가 현재 화면에서 후보와 위치를 찾고, 명시적인 재현·진단에는 추가 flow·legacy 도구를 사용할 수 있습니다. 잘못 만든 세트는 `ny_history retire`로 비활성화할 수 있습니다. 과거 버전은 보존합니다.

계획을 저장하고 실행 중 다시 알려주는 구성은 [oh-my-pi의 todo tracker](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/session/todo-tracker.ts)를 참고했습니다. 기존 pi 확장으로 구현하므로 oh-my-pi/Bun 추가 설치가 필요하지 않습니다.

`ny_checkpoint`는 `snapshotId`와 `note`, 선택적인 `key`·`data`·`state`로 관측한 진행을 기록합니다. 작업에 필요한 필드는 모델이 정의합니다. 예를 들어 전투라면 난이도와 별, 문서라면 페이지와 검토 상태를 담을 수 있습니다. 기존 진행은 `legacy`에 원문 그대로 보존됩니다.

실행 코드에는 특정 게임·시즌·별·CLEAR·전투 횟수에 따른 분기가 없습니다. 작업별 기준은 사용자의 지시와 실행 중 모델이 저장한 스킬/프리셋 **자료**에서 읽습니다. 게임별 기본 프리셋이나 지식은 제공하지 않습니다. 코드가 검사하는 것은 관측의 최신성, 화면/대상 이미지, 좌표/창, 반복 입력과 취소 등 공통 조건입니다. 이미지의 의미와 지침 준수는 모델 판단에 의존합니다.

## 즉석 실행과 저장된 절차

기본 작업 도구는 `ny_target`, `ny_observe`, `ny_click`, `ny_act`, `ny_act_point_add`, `ny_act_point_remove`, `ny_act_point_list`, `ny_scroll`, `ny_wait`, `ny_knowledge`, `ny_time`, `ny_block`, `ny_tools`입니다. 압축된 대화 원본을 읽는 `ny_recall`과 스킬·참조 파일을 읽는 `read`도 유지합니다. 단발 직접 클릭은 `ny_click`, 반복 SELECT 실행에 사용할 좌표 등록은 `ny_act_point_add`를 사용합니다. `ny_act`에는 관측 가능한 작은 `goal`을 주고 필요하면 `until`·`constraints`를 넣습니다. `doneWhen`은 `until`의 호환 별칭입니다. `resume`에 `goal`·`until`·`constraints`를 함께 주면 저장된 범위를 수정하며 생략한 값은 유지합니다. 제약 배열은 교체하고 새 `goal`만 주면 종료 조건도 그 목표로 바뀝니다. `grid_navigation` 기본값은 `false`이며 재개에서 생략하면 저장된 모드를 유지합니다. 모드를 바꾸면 후보를 안전하게 다시 구성하되 미확정 입력의 관측 해소가 항상 먼저이고, 마감은 유지합니다.

ACT는 현재 pi 모델·provider로 후보를 구성하고 SELECT로 필요한 단계만 고릅니다. 기본 클릭 후보는 현재 캡처에 투영·표시한 등록 좌표이며 SELECT는 저장된 `screen`·`description`으로 화면 종류와 실제 표식 위치의 버튼·사용 가능 여부를 확인하고 현재 목표·제약에 따라 판단합니다. 등록 클릭은 별도 locate·LLM 위치 재검증 없이 실행하되 입력 잠금·취소·마감·창 정체성·전송 미상 기록과 입력 후 결과 관측은 유지합니다. 적합한 저장 절차를 재사용할 수 있지만 절차 종료만으로 목표 완료를 뜻하지 않습니다. `done`은 완료 근거, `yielded`는 호출 예산 종료, `needs_decision`은 새 판단 필요, `stopped`는 취소·마감, `error`는 오류입니다. 결과에는 요약·입력 전송/관측 상태·snapshot ID가 들어갑니다. `yielded`는 `ny_act({"resume":"…"})`로 이어가며 전송 미상 입력은 관측으로 해소하기 전 다시 보내지 않습니다.

스크롤 탐색은 전체 목록 영역을 확대하고 이전·현재·과거 탐색 화면을 제한된 작업 메모리로 비교합니다. SELECT가 계속 이동, 짧은 이동, 방향 보정, 재시도, 목표 발견, 경계 도달을 판단합니다. 후보 점수가 비슷하면 확대 관측 후 유력한 두 후보로 다시 선택하며, 해결되지 않을 때 부모 THINK로 돌아갑니다. 경계나 재방문은 전체 작업 완료를 뜻하지 않습니다. 이 중간 이미지들은 부모 대화에 누적하지 않습니다.

`ny_wait({"seconds":10})`은 입력 없이 기다렸다 한 번 관측합니다. `ny_wait({"until":"로딩이 끝나고 결과가 보인다"})`은 같은 공통 실행기에서 화면 조건을 확인하며 기다립니다. 독립 WAIT는 개입이 필요하면 반환하며, 화면 조건을 시간 경과만으로 충족한 것으로 판단하지 않습니다.

`ny_tools(operation:"enable", group:...)`로 추가 도구를 세션 동안 활성화할 수 있습니다. `flow`에는 명시적인 `ny_execute_flow`와 절차 편집, `legacy`에는 `ny_drag`와 후보 세트·이력, `manage`에는 실행·프리셋·계획·체크포인트 편집, `inspect`에는 `ny_locate`·미리보기·추론 설정이 있습니다. 기존 `ny_locate(click:true)`와 `ny_drag`도 공통 입력 기록·결과 확인 경로를 사용합니다. 새 세션과 재시작에서는 기본 도구 목록으로 돌아갑니다.

## ACT 좌표 등록과 투영

세 좌표 도구는 기본 활성이고 **캡처·클릭·모델 호출을 하지 않습니다.** 저장된 전체 스크린샷의 일반 좌표만 받으며 모델에게 중심 상대 비율을 계산시키지 않습니다. 아래 좌표는 형식 예시이므로 실제 관측 이미지에서 확인한 값으로 바꿉니다.

```text
ny_observe({})
ny_act_point_add({
  "snapshotId": "관측 결과의 id",
  "id": "confirm",
  "label": "확인 버튼",
  "screen": "확인 팝업",
  "description": "팝업 하단의 확인 버튼. 팝업을 닫는다.",
  "box": {"x": 0.7, "y": 0.65, "width": 0.2, "height": 0.1},
  "jitter": 0.15
})
ny_act_point_list({"snapshotId": "관측 결과의 id"})
ny_act({"goal": "열린 확인 팝업을 닫는다"})
ny_act_point_list({})
ny_act_point_remove({"id": "confirm"})
```

- `point:{x,y}` **또는** `box:{x,y,width,height}` 하나만 지정합니다. 원점은 **전체 스크린샷 왼쪽 위**, 축은 오른쪽·아래 방향, 단위는 기존 0–1 정규화 좌표입니다. crop 좌표·픽셀·중심 상대 비율을 인자로 넘기지 않습니다. 같은 `id`로 다시 add하면 해당 등록을 갱신합니다.
- 등록 `id`는 소문자 영문으로 시작하는 1–32자의 영문 소문자·숫자·`_`·`-`입니다(`^[a-z][a-z0-9_-]{0,31}$`). SELECT 제어용 예약 ID와 Windows 장치명은 거부합니다. 한국어 이름은 `label`에 넣습니다. `label`은 160자, `screen`·`description`은 각각 2000자까지입니다.
- `screen`에는 화면·팝업 종류, `description`에는 버튼 자체의 위치·역할·직접 효과만 적습니다. 랭킹·점수·재화·상대 이름 같은 변동값, 목표·전략·진행 상황은 등록하지 않고 현재 `ny_act`의 목표·제약에 둡니다. SELECT가 현재 화면 종류와 표식 위치의 버튼 설명·사용 가능 여부를 함께 확인합니다.
- 저장 형식은 v2이며 등록의 `when`·`expectation` 필드는 제거했습니다. 기존 v1 데이터는 화면 종류와 버튼 설명을 명시하여 변환해야 하며, 옛 조건을 자동 해석하거나 새 필드로 복사하지 않습니다.
- 위치가 불확실하면 `ny_tools`의 `inspect`를 활성화해 `ny_locate({snapshotId,target})`로 조사하고, 반환된 `snapshotId`와 `point`를 그대로 등록합니다. `ny_locate`는 독립 기능이며 ACT의 `grid_navigation:false`에서도 작동합니다.
- add는 저장된 메타데이터와 주석 이미지를 반환합니다. list에 `snapshotId`를 주면 해당 앱의 모든 등록과 투영된 박스·ID·실제 표본 클릭점이 표시됩니다. 투영 불가 ID도 따로 보고합니다. 인자 없는 list는 저장된 등록만 읽고 **새 캡처를 만들지 않습니다.** remove는 등록 하나만 지우며 앱·파일·화면에는 입력하지 않습니다.
- 가까운 등록점의 ID 라벨은 서로 겹치거나 클릭 표식을 가리지 않도록 이미지 안에서 재배치하고, **직선 연결선으로 원래 클릭점과 연결**합니다. 실제 클릭 좌표·박스·이미지 크기는 바꾸지 않습니다. 배치 공간이 부족하면 라벨을 숨기거나 겹쳐 반환하지 않고 오류로 알립니다.
- 등록 범위는 **현재 실행**입니다. 원본 snapshot ID·기준 이미지 크기·앱 정체성과 생성/갱신 시각을 함께 보관합니다. `snapshot.knowledgeAppId`로 앱을 구분하고 그 값이 없는 과거 캡처에만 앱 정체성 대체값을 사용합니다. 다른 실행에 자동으로 전파하거나 좌표를 임의 재사용하지 않습니다.
- 박스의 `jitter`는 박스 폭·높이의 비율이며 기본 `0.15`, 범위 `0–0.45`입니다. 중심에 더 가까운 점이 자주 나오는 삼각 분포로 각 축을 표본 추출하고 점은 박스 내부에 유지합니다. `0`이면 중심 고정이고 point 등록은 항상 jitter `0`입니다. 등록 미리보기의 표본은 실행 예약점이 아니며 ACT는 최신 캡처마다 새로 투영·표본 추출하여 **선택 전에 실제 입력점을 표시**합니다. 이전 캡처·재개·크기 변경 뒤의 표본 픽셀을 재사용하지 않습니다.
- 모든 관련 등록은 이미지·목록에서 누락 없이 제공하고 후보 생성은 그중 최대 4개 ID를 고릅니다. SELECT의 2–12 선택지 제한은 유지합니다. 선택하지 않은 등록을 삭제하거나 목록에서 조용히 잘라내지 않습니다.
- `grid_navigation`은 기본 OFF이며 `ny_act`는 **등록 클릭만** 허용합니다. 등록이 없으면 생성 모델도 호출하지 않고 `candidates_needed`를 반환하며 **격자로 자동 폴백하지 않습니다.** `ny_act({"goal":"…","grid_navigation":true})`로 명시할 때만 기존 생성 클릭·드래그·격자 탐색을 허용합니다. 기본 혼합 ACT에서 드래그도 내부 locate가 필요하므로 허용하지 않지만, 독립 `ny_scroll`과 명시적 flow API는 기존대로 동작합니다.
- 기본 ACT의 완료 확인도 격자 없는 현재 화면을 사용합니다. `grid_navigation:true` 또는 스크롤 전용 경로에서는 기존 참조 격자·드래그 전후 비교를 유지합니다.

Windows Cua + 실제 Qwen으로 별도 네이티브 시험 창의 영역을 등록하고 기본 ACT를 실행해 카운터 `0→1`을 확인했습니다. 입력은 1회, SELECT는 선택·입력 결과·목표 확인의 3회였으며 grid 위치 탐색은 호출하지 않았습니다. 등록점 사용은 위치 탐색을 없애지만 후보 생성·행동 선택·결과 확인까지 없애는 것은 아닙니다.

### 내부 중심 상대 저장과 중앙 레터박스

기준 전체 이미지가 \(W_r\times H_r\), 입력 정규화 점이 \((u,v)\)이면 내부에 \(c_x=u-0.5,\ c_y=v-0.5\)와 기준 크기를 저장합니다. 박스는 중심을 같은 방식으로 저장하고 정규화 폭·높이도 보관합니다. 새 이미지 \(W_n\times H_n\)에는 아래 식으로 균일 배율과 중앙 여백을 적용합니다. 이 식은 구현 설명이며 **도구 인자는 여전히 기존 point/box**입니다.

```text
s = min(Wn / Wr, Hn / Hr)
ox = (Wn - s * Wr) / 2
oy = (Hn - s * Hr) / 2
xn = Wn/2 + s * cx * Wr = ox + s * u * Wr
yn = Hn/2 + s * cy * Hr = oy + s * v * Hr
새 정규화 점 = (xn / Wn, yn / Hn)
새 박스 픽셀 크기 = (s * 원본 박스 폭 * Wr, s * 원본 박스 높이 * Hr)
```

예를 들어 1000×600 이미지의 `point:{x:0.8,y:0.75}`는 1400×600 이미지에서 배율 1, 좌우 여백 200을 가정해 픽셀 (1000,450), 새 정규화 점 약 (0.714286,0.75)로 옮겨집니다. 단순히 새 폭의 80%를 클릭하지 않습니다.

**자동 검은 띠 감지는 없습니다.** 내용이 중앙에서 같은 비율로 확대·축소되고 남는 공간이 대칭 레터박스라는 가정입니다. 비대칭 여백·좌상단 고정 내용·잘림·UI 재배치·서로 다른 종횡비 재배치는 보장하지 않습니다. 이때 새 관측으로 대상을 다시 등록해야 합니다. 주석과 화면·버튼 설명 확인도 앱별 레이아웃 변화의 보증이 아닙니다.

## 관측 기반 직접 클릭

`ny_click`은 기본 활성 도구입니다. `ny_observe`의 이미지를 보고 planner가 정한 좌표로 **한 번만** 클릭하고, 입력 후 스크린샷을 반환합니다. 아래 `snapshotId`는 실제 관측 결과의 `id`로 바꾸고, 좌표는 해당 이미지에서 확인한 대상에 맞게 지정합니다.

```text
ny_observe({})
ny_click({
  "snapshotId": "관측 결과의 id",
  "label": "확인 버튼",
  "intent": "현재 대화상자를 확인한다",
  "point": {"x": 0.72, "y": 0.81}
})
```

`point`는 crop이 아닌 **전체 창 기준 0–1** 좌표입니다. `point`, `box`, `regionPath`, `gridPoint` 중 하나만 지정합니다. 선택적인 `anchor`와 `anchorRegion`은 동시에 쓰지 않습니다. 입력 잠금·미해결 입력·중단·마감·창과 좌표 기하·기준/현재 대상 이미지 비교는 유지하지만, 클릭 전후 **SELECT·LLM 확인은 전혀 하지 않습니다**. `ny_locate`는 위치가 불확실할 때 쓰는 선택적인 SELECT 보조 도구이며 필수 단계가 아닙니다. `ny_preview`로 같은 좌표를 입력 없이 표시할 수도 있습니다.

결과의 `selectCalls`는 `0`이며, `inputSent:true`는 전송만 뜻하고 목표 성공을 뜻하지 않습니다. planner가 반환된 스크린샷으로 결과를 판단합니다. `inputSent:null`/전송 미상이나 입력 후 캡처 실패는 저장된 `continuationId`의 복구 경로로 해소하며 같은 클릭을 무작정 재전송하지 않습니다. 확장 변경은 실행 중인 TUI의 `/reload` 또는 재시작 후 적용됩니다.

Windows Cua의 실제 `ny_click` 등록 경로를 별도 네이티브 시험 창에서 실행하여 카운터 `0→1`, SELECT 0회, 입력 후 이미지 반환을 확인했습니다. 게임 창은 이 검증에서 조작하지 않았습니다. 실패 결과는 `reason`과 함께 가능한 원본 `error` 메시지를 반환합니다.

## 관측 재확인과 연결 복구

`ny_observe(snapshotId, verify:true)`는 과거 이미지와 현재 화면에서 같은 행동을 이어갈 수 있는지 확인하고 최신 이미지를 반환합니다. 동일 픽셀은 모델 호출을 생략하는 빠른 경로이고, 다르면 비교 이미지로 Y/N SELECT를 합니다. SELECT 기반 행동 재확인에서는 클릭 대상의 정체성·위치·가림을, 드래그는 같은 스크롤 영역이 열려 있고 경로가 막히지 않았는지를 확인합니다. SELECT의 YES를 추가 픽셀 오차 검사로 다시 거부하지 않습니다. 배너·영상·카드 애니메이션은 화면 전환과 구분합니다. 창의 PID·ID·크기·위치가 달라졌거나 판단이 불명확하면 기존 좌표를 실행하지 않습니다. 시간 경과만으로 화면이 바뀌었다고 판단하지 않습니다. `verify:true`는 선택 사항이며 `ny_click`의 선행 조건이 아닙니다.

Cua 요청 제한은 `desktopTimeoutSeconds`로 설정하며 기본 180초입니다. 읽기 전용 캡처가 타임아웃이면 새 파일로 한 번만 재시도합니다. 새 화면을 얻지 못한 상태에서는 같은 화면이라고 판정할 수 없습니다. SELECT 기반 실행에서는 Cua 세션 만료로 입력이 **실행 전에 거부됐음이 확인된 경우** 해당 private 세션을 복구하고 화면 SELECT 검증 후 한 번 재시도합니다. `ny_click`은 이 SELECT 재시도 경로를 사용하지 않습니다. 입력 타임아웃은 실행 여부가 불명확하므로 자동 재전송하지 않습니다. 공유 Cua 데몬이나 다른 프로그램의 세션은 재시작하지 않습니다.

## 격자 좌표 탐색

`ny_locate(target, snapshotId, click=false)`는 `ny_tools`의 `inspect` 그룹에서 활성화하는 독립적인 SELECT 보조 위치 조사 도구입니다. ACT의 `grid_navigation` 설정과 무관하게 사용할 수 있습니다. 기본 ACT는 등록 좌표만 클릭하므로 반환된 `point`와 `snapshotId`를 `ny_act_point_add`에 전달합니다. planner가 화면에서 정한 좌표는 `ny_click`으로 직접 클릭할 수도 있습니다. 위치가 불확실할 때 내부 1토큰 SELECT로 탐색하며 A–I의 3×3 격자, 확대·축소·8방향 MOVE와 별도 십자선 확인을 사용합니다. 기본·최대 예산은 이동·검증을 포함한 SELECT 20회이며 기존 4×4 `regionPath`는 대략적인 시작 힌트일 뿐입니다. 확정하면 전체 창 기준 0–1 좌표를 반환하고 불확실하거나 예산이 끝나면 좌표를 반환하지 않습니다. 탐색 자체는 실제 마우스를 움직이거나 ACT 격자 모드를 켜지 않습니다.

`ny_locate`의 기본값은 좌표 반환뿐입니다. 1회 클릭은 `click:true`로 요청하며 `expectation`이 필요합니다. `anchor` 또는 `anchorRegion`은 선택적인 문맥 힌트입니다. 좌표 확인과 새 화면·창·대상 검사를 통과해야 클릭합니다. 클릭 요청 결과는 `inputSent`와 `clicked`로 입력 전송 여부를 명시합니다. `reason:input_not_sent`이면 클릭되지 않았고, `input_sent`는 입력 전송만 뜻하며 성공 판정은 아닙니다. 반환된 현재 이미지를 재사용하고 같은 이미지를 얻으려고 다시 observe할 필요는 없습니다. SELECT 없이 직접 좌표로 클릭하려면 별도 기본 도구 `ny_click`을 사용합니다. 좌표 반환 모드는 위치 확인·미리보기에 사용할 수 있으며, 오래된 화면에서 찾은 좌표를 현재 상태로 간주하지 않습니다.

탐색은 본 대화 전체를 복제하는 pi `/fork`가 아니라, 시각적 목표·짧은 선택적 `constraints`·기준 화면으로 시작하는 내부 대화 분기입니다. 전체 작업 이력은 복제하지 않으며, 작업 정책과 다음 행동의 선택은 부모 planner가 담당합니다. 확대는 기존 요청/응답 뒤에 추가하고 축소는 부모 분기의 공통 prefix로 되돌리고, 이미 실패한 영역은 다시 고르지 않도록 기록합니다. paged/prefix cache가 있다면 이를 재사용할 수 있지만 캐시 적중을 보장하거나 서버 설정을 바꾸지는 않습니다. 중간 이미지와 결정 기록은 로컬 `.nyatinorma/locate/`에 남기며, 주 대화에는 최종 결과와 근거 이미지만 전달합니다. 클릭한 경우에는 행동 후 화면을 전달합니다.

## 데이터와 설정

`nyatinorma.json`은 로컬 전용이며 Git/배포에 포함하지 않습니다. 새 설치는 `nyatinorma.example.json`을 복사하고 주소·모델·대상 창을 설정합니다. `NYATINORMA_OLLAMA_URL`/`NYATINORMA_MODEL` 환경변수도 지원합니다. `contextWindow`·`maxTokens`·`reasoning`은 pi에 등록할 모델 메타데이터이며 Ollama의 상주/컨텍스트 설정을 변경하지 않습니다.

커스텀 provider의 `contextWindow`는 `.nyatinorma/pi/models.json`에 초기값으로 등록합니다. OpenAI 호환 서버가 `/models`에 유효한 `max_model_len`을 제공하면 시작·모델 선택·사용자 요청 시 확인하여 **설정값보다 크거나 작아도 서버 한도를 우선 적용**합니다(조회 결과는 60초 캐시). 현재 모델과 런타임 레지스트리를 함께 갱신하며, 한도를 제공하지 않거나 조회할 수 없는 서버에서는 기존 값을 유지합니다. 등록 파일과 서버 설정은 자동 변경하지 않습니다. 모델 등록이나 확장 코드를 수정한 뒤에는 실행 중인 TUI에서 `/reload`로 다시 읽습니다.

긴 세션은 pi의 compaction 경계에서 줄입니다. 스크린샷을 매 요청마다 이동식으로 제거하지 않고, compaction 사이에는 과거 메시지와 이미지를 유지하여 prefix cache 재사용을 방해하지 않습니다. 시작·모델 선택 시에는 이전 모델의 토큰 사용량을 그대로 믿지 않고 pi의 추정기로 다시 계산하며, 새 한도의 compaction 기준을 넘으면 정리를 실행합니다. 일반 실행 중에는 pi의 임계치·컨텍스트 초과 복구·`/compact` 호출이 같은 정책을 사용합니다.

정리 방식은 **오래된 도구 결과·이미지 생략 → pi 의미 요약 → 요약 실패 시 오래된 실행 내역 절단** 순서입니다. Compaction 경계에서 최근 원본 구간을 약 4K 추정 토큰으로 좁히되, 최신 이미지 관측과 도구 호출/결과 묶음은 보존합니다. 묶음 자체가 크면 4K를 넘을 수 있습니다. 기계적 정리 기록은 컨텍스트의 10% 또는 6K 중 작은 크기 이하로 제한하고, 두 번 연속 기계적으로 정리했다면 다음에는 의미 요약을 시도합니다. 전체 복구 목표는 `(contextWindow − reserveTokens) × 70%`이며, 현재 모델이 보고한 실제 사용량이 추정보다 크면 그 비율만큼 목표와 요약 예산을 낮춥니다. 이전 모델 또는 이전 compaction 전의 사용량은 보정에 쓰지 않습니다.

의미 요약은 이전 요약까지 병합하며, 요약용 추론은 끄고 기존 pi provider를 사용합니다. 출력 토큰 한도에 잘린 요약은 저장하지 않습니다. 실패하거나 절감량이 부족하면 사용자 지시·이전 요약·최근 원본 구간을 보존하면서 오래된 실행 내역을 제거합니다. 이마저 충분히 줄이지 못하면 이유를 표시하고 중단합니다. 각 단계는 경계당 한 번만 시도합니다. `/compact 추가 지시`는 도구 정리를 건너뛰고 의미 요약부터 요청합니다.

원본 세션·캡처는 보존됩니다. 모델은 `ny_recall`로 원본 텍스트를 검색하거나 특정 기록의 이미지 한 장을 다시 읽을 수 있고, `ny_observe(snapshotId)`로 저장된 화면을 볼 수 있습니다. 기계적 절단은 의미 요약보다 정보를 더 잃을 수 있어 TUI에 경고합니다. 토큰 추정은 서버 tokenizer와 다르며 컨텍스트 한도 보장의 대체물이 아닙니다. [OMP의 compaction 설계](https://github.com/can1357/oh-my-pi/blob/main/docs/compaction.md)에서 방법별 효과 판정과 다음 방법으로 넘어가는 원칙을 참고했습니다. OMP 전체 실행 순서·백그라운드 선행 요약을 이식한 것은 아니며, OMP 소스나 추가 의존성을 포함하지 않습니다.

`nyatinorma.json`: Ollama 주소/모델, Cua 실행 경로/대상 창, 실행 예산, 선택 기준. 기존 Ollama 설정이나 전역 pi 설정을 변경하지 않습니다. pi 설정은 `.nyatinorma/pi`에 격리되고, 사용자가 바꾼 테마·UI·추론 설정을 시작 시 덮어쓰지 않습니다.

`.nyatinorma/skills/computer-use`: 공통 지식. `.nyatinorma/skills/<knowledgeAppId>`: 앱 패키지로 `SKILL.md`, `notes/`, `presets/`, `sets/`, `evidence/`를 포함합니다. 프리셋·세트의 기존 파일은 다음 시작에 원본을 보존하고 복사하며 이후 패키지 쪽을 사용합니다. 설정된 앱을 선택하면 기존 `knowledgeAppId` 패키지를 유지합니다. 다른 앱은 선택된 앱의 식별자로 별도 패키지를 만들며, 설정된 앱의 기존 파일을 복사하지 않습니다. 패키지는 지식 자료이며 모델·드라이버·앱 설치를 포함하지 않습니다.

`.nyatinorma/runs/<실행ID>`: 자동 생성된 기록, 계획, 진행, 후보, 로그. `.nyatinorma/pi/sessions`: 대화와 실행 연결 이력. `.nyatinorma/captures`: 원본 이미지와 메타데이터. `.nyatinorma/feedback.jsonl`: 교정 기록. 실행 완료 상태는 스킬로 복사하지 않습니다. 새로 저장한 지식/공유 세트의 근거는 패키지 내부 상대 경로로 보존합니다. 기존 실행의 모든 과거 이미지를 패키지로 옮기지는 않습니다.

## 검증

- 테스트 정책은 **minimal, core logic only**입니다. 핵심 동작의 대표 시나리오와 실제 발생한 버그의 최소 회귀 검증만 유지합니다. 가상의 엣지 케이스·프롬프트 문구·내부 연결·중복 검증은 추가하지 않습니다. 상세 기준은 [AGENTS.md](AGENTS.md)에 있습니다.
- 타입 검사·테스트·omp 빌드 및 새 Eval 커널의 설치 번들 로딩을 확인했습니다.
- Windows omp에서 가려진 테스트 창의 캡처·입력·대기와 포그라운드 창 유지, 중단·재개를 확인했습니다.
- MuMu 게임 실기에서 `clef-flash:9b` 판정 39회와 두 판 승리를 확인했습니다. 직접 클릭 3회와 상위 모델의 결과 확인 보완이 필요했으므로 **완전 자율 등반 검증은 아닙니다**. 모델별 오판과 미검증 범위는 [omp 가이드](integrations/omp/USAGE.md#검증과-한계)에 정리했습니다.
- 독립 실행의 [구조·설정·개인정보 점검](docs/architecture-and-privacy.md), [지식과 기록 검증](docs/knowledge-and-sessions.md)은 별도 기록입니다. 새 코드는 재시작 후 적용하며 장기 무개입 실행은 보장하지 않습니다.

```sh
npm test
npm run typecheck
npm run probe                 # 기존 모델의 SELECT/logprobs 확인, 게임 입력 없음
npm run observe               # 실제 게임 창 이미지 캡처, 입력 없음
npx tsx src/cli.ts vision-probe  # 같은 Ollama 모델에 게임 이미지 전달, 입력 없음
```

기본 pi 도구에서는 범용 shell/file 편집을 제외하고 작업·관측·정의·실행·기록 도구를 제공합니다. TUI의 핵심은 pi를 재사용하며 게임 실행 정책은 이 프로젝트의 TypeScript 확장에 있습니다.
